# Componentes

Componentes internos relevantes por camada/módulo. Todos abaixo têm código real, exceto o parser `.vpp` (ainda planejado, fora do escopo das 5 tasks do MVP).

## Camada de visualização (frontend)

- **Design system e shell de diagrama** (`src/features/diagram-shell/`, real — TASK-006/007/010, ADR-002) — tokens de cor/tipografia exatos do artefato-protótipo validado (`src/index.css`, dark/light via `prefers-color-scheme`+`[data-theme]`), componente `DiagramShell` (grid de 3 colunas topbar/sidebar/canvas/inspector, com `canvasProps` para quem precisa de ref/handlers na própria área do canvas), `Toast`/`useToast`, `Modal` (genérico, `.modal-overlay`/`.modal`, fecha por ×/clique fora/Esc — TASK-010, usado por `ImportExportControls` e `ClassPickerModal`) e `canvasTransform`/`useCanvasZoomPan` (matemática de zoom/pan + hook, compartilhados por Diagrama de Classes e de Objetos). Visão do Sistema (TASK-009) não usa `DiagramShell`/a parte de canvas/zoom-pan — só reaproveita os tokens de `src/index.css`, com seu próprio shell full-bleed (`.system-view-shell`, topbar + `.ov-nav`/`.ov-detail` 280px/1fr).
- **Alternância de tema claro/escuro** (`src/features/theme/`, real — TASK-019, ADR-007) — o hook `[data-theme='dark'|'light']` do design system (existia desde o ADR-002/TASK-006, sem uso) ganhou um controle real: `theme.ts` (`getStoredTheme`/`applyTheme`/`applyStoredThemeOnBoot` + hook `useTheme`, sem `useEffect` — o estado inicial já reflete o que `applyStoredThemeOnBoot` aplicou no `<html>` antes do primeiro render) e o componente `ThemeToggle` (ícone ☀️/🌙 único, reaproveitado sem mudança). Persistência só em `localStorage` (`classmap-theme`), nunca no Supabase — decisão de `ADR-007` (rejeitou sincronizar entre dispositivos por esforço desproporcional sem pedido de uso multi-dispositivo). `applyStoredThemeOnBoot()` roda em `main.tsx` antes de `createRoot`, para não haver flash do tema errado. Montado fixo (não via prop) nas 3 superfícies de topbar autenticadas: `AppLayout` (`.app-header-actions`, novo wrapper), `DiagramShell` (irmão fixo após `.topbar-actions` — cobre Diagrama de Classes/Objetos de uma vez) e `SystemViewPage` (fora do bloco `!readOnly`, continua visível em modo `visualizador`).
- **Diagrama de Classes** (`src/features/class-diagram/`, real — TASK-003, canvas avançado na TASK-007) — cards de classe (`.node-box`) e conectores UML ortogonais dentro do shell da TASK-006, com zoom/pan, modo de conexão (clicar origem→destino), busca+stats na sidebar e inspector fixo (substituiu o painel flutuante antigo). `DiagramEditorPage` não usa mais `AppLayout` — é full-bleed com o shell próprio (decisão da TASK-007). **TASK-014/ADR-005**: `color?` opcional em `DiagramClass`, paleta fixa de 22 cores (`ClassColorGrid.tsx`, mesmo padrão de seletor do `EdgeTypeGrid`), aplicada via `--node-color`/`color-mix()` no `ClassCard` — interna ao ClassMap, nunca entra no schema de import/export (ver `contrato-ia-diagrama`).
- **Diagrama de Objetos** (`src/features/object-diagram/`, real — TASK-004, canvas avançado na TASK-008) — instâncias, valores de atributo herdados da classe por snapshot (RN-01 da TASK-004), agora com o mesmo shell/zoom-pan do Diagrama de Classes, paleta `--object-accent` (`.node-box.object`) e modal (`ClassPickerModal`) para criar um objeto a partir de uma classe existente, substituindo o formulário de 2 selects da toolbar antiga. `ObjectDiagramPage` também não usa mais `AppLayout`. **TASK-017/ADR-006**: `links: ObjectLink[]` em `ObjectDiagramContent`, modo de conexão reaproveitando `class-diagram/connectMode.ts`, `ObjectLinkConnector.tsx` novo (linha reta ortogonal com ponto de controle, sem os 5 símbolos UML — link entre instâncias não é relação entre classes) — também nunca entra no schema de import/export.
- **Visão do Sistema** (`src/features/system-view/`, real — TASK-004, layout do artefato na TASK-009) — navegação módulo → entidade na lateral (`.ov-nav`/`.ov-entity-btn`, dot indicador + estado ativo), painel de detalhe (`.ov-detail`) com breadcrumb, nome da entidade em `IBM Plex Mono`, pills de resumo, tabela de campos com badges de restrição (`.ov-flag`/`.pk`/`.fk`/`.nn`, mais `AI`/`UQ` neutros para os 2 flags sem cor própria no artefato), métodos de API como lista (`.ov-method-row`) e regras de permissão como cards (`.ov-perm-card`, condição destacada em `.ov-perm-cond`). `SystemViewPage` também não usa mais `AppLayout` — full-bleed com shell próprio (`.system-view-shell`), igual às outras duas visualizações; a lógica/dados (`contentOperations.ts`/`types.ts`) não mudou, só a apresentação (RN-02 — os 3 blocos continuam sempre presentes). **TASK-018**: criação de módulo pede um nome (modal reaproveitando `Modal`, mesmo padrão da TASK-016 para diagrama), em vez de nascer sempre "Novo módulo"; `.ov-module-title` também passou a ser editável inline (`.ov-module-title-input`) quando `!readOnly`, chamando `updateModule` (já existia em `contentOperations.ts` desde a TASK-004, sem uso até então). **TASK-021/TASK-024**: módulo e entidade agora podem ser excluídos — `removeModule`/`removeEntity` (`contentOperations.ts`, ambos existiam desde a TASK-004 sem nenhum componente chamando) ligados a um botão "×" (`.ov-row-remove`, mesma classe já usada em campo/método/regra) ao lado do nome, com `Modal` de confirmação avisando o que será perdido (`describeEntityLoss` para entidade) — sem exigir digitar o nome, diferente de `DeleteConfirmModal` (critério: edição de conteúdo de um diagrama, não hard delete de linhas do banco). **TASK-020**: o nome do diagrama (topbar das 3 visualizações) também passou a ser editável a qualquer momento (`renameDiagram`, `src/lib/supabase/queries.ts`), não só na criação.
- **Navegação e gestão de acesso** (`src/features/navigation/`, real — TASK-002, estendido nas TASK-011/013/016/022) — `OrganizationsPage`/`ProjectsPage`. **TASK-011/ADR-003**: exclusão (hard delete) de organização/projeto, via `DeleteConfirmModal.tsx` (reaproveita `Modal` do design system — confirma digitando o nome exato antes de habilitar o botão), chamando `deleteOrganization`/`deleteProject` (`src/lib/supabase/queries.ts`); RLS/cascade já existentes desde a TASK-001, nenhuma migration nova. **TASK-013/ADR-004**: `AccessManagementModal.tsx` genérico (parametrizado por organização/projeto) — vincular usuário já cadastrado por e-mail (via RPC `find_user_id_by_email`, TASK-012), listar/alterar papel/revogar acesso, sobre as políticas RLS de `organization_members`/`project_members` já existentes (TASK-001), sem RLS nova; lista de membros mostra `full_name`/id truncado, não e-mail (`profiles` não expõe e-mail de outro usuário). **TASK-026/ADR-010**: o modal ganhou um segundo modo, "Criar conta nova" (alternância ao lado do já existente "Já tem conta") — e-mail + senha temporária (botão "Gerar senha") + papel, chamando `createUserWithPassword` (Edge Function `admin-create-user`, TASK-025); sucesso mostra a senha uma única vez, num aviso persistente até o modal fechar (RN-02); `AccessRoleOption` ganhou `description` — legenda curta do papel, ao lado do seletor nos dois modos. No modal de **projeto**, criar conta sempre inclui o vínculo de organização (`member`) na mesma chamada (RN-01), com texto de ajuda explicando isso. **TASK-016**: criação de diagrama pede um nome (modal reaproveitando `Modal`), em vez do nome vir só do label do tipo. **TASK-022/ADR-008**: `DiagramsPage` deixou de listar diagramas diretamente — agora mostra 3 cards de tipo (Classes/Objetos/Visão do Sistema) com contagem; `DiagramTypeListPage.tsx` (novo) tem a lista + criação filtrada por tipo (lógica que antes vivia em `DiagramsPage`); a rota compartilhada `/diagrams/:x` passou a ser atendida por `DiagramsRouteDispatcher.tsx` (novo), que decide pelo valor do parâmetro entre a lista por tipo (dentro de `AppLayout`) e o `DiagramRouterPage` original (full-bleed, sem mudança) — mesmo padrão de despacho por valor já usado ali para `diagram.type`. `diagramTypeLabels.ts` (novo) centraliza `DIAGRAM_TYPE_LABELS`/`DIAGRAM_TYPES`/`isDiagramType`, compartilhado pelas 3 telas/despachante.
- **Autenticação** (`src/features/auth/`, real — TASK-002, estendido nas TASK-023/025/026) — `AuthContext` não mudou. **TASK-023/ADR-009 (superseded pelo ADR-010)**: `LoginPage.tsx` chegou a ganhar uma alternância Entrar/Criar conta — **revertida na TASK-026** depois de o autocadastro esbarrar no limite de 2 e-mails/hora do Supabase (ver ADR-010); `LoginPage.tsx` hoje só tem o formulário de entrar, `signUp` foi removido de `queries.ts` (sem uso). **TASK-025/026/ADR-010**: o admin passa a criar a conta do colega diretamente, via a Edge Function `admin-create-user` (`supabase-multitenant`) chamada por `createUserWithPassword` (`queries.ts`) a partir do `AccessManagementModal` (organização e projeto) — usuário nasce com `user_metadata.must_change_password = true`. `RequireAuth.tsx` passou a checar essa flag e renderiza `ForcePasswordChangePage.tsx` (novo, 100% client-side via `auth.updateUser`) no lugar de `children` até a pessoa trocar a senha — a sessão atualiza sozinha (`AuthContext` já ouvia `USER_UPDATED`), sem reload manual. `OrganizationsPage` ainda orienta, no estado vazio, quem está autenticado sem nenhuma organização a pedir acesso a um admin (mostrando `useAuth().session.user.email`) — mantido como fallback (não há mais autocadastro que leve a esse estado como caminho principal, mas nada impede alguém logar sem vínculo se um provisionamento falhar antes do vínculo).

## Camada de dados/autorização

- **Client Supabase** (`src/lib/supabase/`, real — TASK-001/002) — queries sempre respeitando RLS, dono: papel `supabase-multitenant`. Integração com Realtime Presence ainda planejada (roadmap "Colaboração", fora do MVP). **TASK-012/ADR-004**: RPC `find_user_id_by_email` (`supabase/migrations/20260829090000_rpc_find_user_id_by_email.sql`, `security definer`, mesmo padrão de `create_organization`) — localiza um usuário já cadastrado pelo e-mail (case-insensitive), retornando só o `id` (nunca outro campo de `auth.users`); base da TASK-013. Validada localmente (Postgres via Docker); ainda não aplicada ao projeto Supabase de produção (`classmap`) — ver pendências da TASK-012.
- **Edge Function `admin-create-user`** (`supabase/functions/admin-create-user/`, real — TASK-025, ADR-010) — primeiro (e único) componente de backend próprio do ClassMap, e único código do projeto que usa a `service_role key`. Recebe e-mail/senha/organização (e opcionalmente projeto+papel) de um admin autenticado; checa `is_org_admin`/pertencimento do projeto com o client do próprio JWT do chamador (sem duplicar autorização); só então usa um segundo client com a service role para `auth.admin.createUser` (usuário nasce confirmado, `user_metadata.must_change_password = true`, nenhum e-mail disparado); insere os vínculos de `organization_members`/`project_members` de volta com o client do chamador, autorizado pela RLS já existente. Consumida pela TASK-026 via `createUserWithPassword` (`src/lib/supabase/queries.ts`, `client.functions.invoke`). Ver `supabase/README.md`, seção "Provisionamento de usuário pelo admin — `admin-create-user`".
